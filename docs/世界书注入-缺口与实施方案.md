# 世界书注入 · 缺口与实施方案（issue 草稿）

> 状态：待拍板 / 未开始
> 发现来源：2026-11-25 A 线交叉验证
> 归属：B 线（世界书）
> 已确认口径：**按岗位注入**、**`worldbook_book` 增加 `job_code` 并回填**

## 一、背景

issue #1 要求「世界书半」：YAML 放 `game_data/worldbooks/<code>.yml`，启动扫描入库，并提供 `/api/worldbooks` 查询。前半已完成，但入库结果没有进入对话注入，等于只做了一半。

## 二、现状核实

| 事实 | 证据 |
|---|---|
| 两表已建、启动同步已生效 | `schema-h2.sql` 的 `worldbook_book` / `worldbook_entry`；`WorldbookSyncService.syncAll()` 启动执行，当前入库 `java`、`frontend` 两本，各 4 条 |
| 只读接口可用 | `GET /api/worldbooks` 返回 2 本；单本详情带 entry（2 条 `always`、2 条 `keyword`） |
| 对话没有读两张表 | `ChatService.java:394` 只有 `Worldbook.parse(speaker.getWorldbook())`，全库没有从 `worldbook_book` / `worldbook_entry` 读取的代码 |
| 现有注入实际为空 | 4 张卡的 `interviewer.worldbook` CLOB 列均为空，因此 `parse` 返回 null，注入被跳过 |
| 表缺 `job_code` | `worldbook_book` 只有 `code / name / description / source_path / enabled / sort_order`；`WorldbookSummary` / `WorldbookDetail` 也没有 `jobCode` |
| 对话链路有两条 | 自由对话走 `ChatService`（`ChatController` / `SessionController` 的 `/messages`）；剧本面试走 `ScriptPlayController → InterviewEngine → AiDialogueEvent / freeDialogueTurn → DialogueWriter` |
| 剧本链路也没有世界书与知识注入 | `engine` 包内 `Worldbook`、`KnowledgeInjector` 均 0 命中；剧本链路只调 `DialogueWriter.writeTurn(ctx, messages, userSeq)` |
| 岗位信息在会话上 | `interview_session.job_code` 非空；`ChatService` 已在用 `session.getJobCode()` |
| 角色表没有岗位字段 | `interviewer` 表与实体均无 `job_code`，角色 code 是 `strict / pressure / friendly / expert`，与 `java / frontend` 不是一套编码 |

## 三、缺口

1. **注入未接线**：`always` 的「公司背景」「岗位职责」不会进 system，`keyword` 条目也不会触发。**且这不是一处接线能解决的**——自由对话与剧本面试是两条独立的生成链路，只改 `ChatService` 时剧本链路仍不会生效，而剧本是答辩演示的主路径。
2. **缺 `job_code`**：书属于哪个岗位只能靠 `code == jobCode` 的隐含约定，接口也不暴露岗位。
3. **概念边界未写清**：`docs/03-待办与实施计划.md` 把「世界书 → 岗位知识库」定义为 RAG 语料层，而 K 系列 `knowledge` 模块已在做按回答检索的注入。两套来源若不区分定位，会出现重复内容与无谓 token 开销。

## 四、已确认的决策

- **按岗位关联**：用 `session.jobCode` 找 `job_code` 相同的书，不新增角色级关联表、不动角色卡。
- **注入下沉到引擎上下文**：自由对话与剧本面试两条链路都要覆盖，不能只改 `ChatService`。
- **装载器与注入器都放 `cn.edu.zjut.interview.worldbook` 包**：`Worldbook` 的构造器、`Entry` 构造器、`Activation.always()/keyword()` 都是包私有，换包就得额外暴露内部结构。
- **补 `job_code` 列并回填**，接口返回 `jobCode`，对齐 issue 原文四字段。本期**单值**：一本书对应一个岗位；「一本书服务多个岗位」是后续话题，需要改成 JSON 数组或关联表，本期不做。
- **不采用「写回 `interviewer.worldbook` CLOB」**：角色与书无法对应（角色表没有岗位字段），且会形成双真相源、覆盖人工编辑。
- **定位分工**：世界书只承载「固定岗位背景」（公司、团队、岗位职责，建议全部 `always` 且控制在 3~5 条、单条 300 字内）；技术知识点继续留在 `knowledge`。

## 五、实施方案

### 1. DDL 与同步（`schema-h2.sql`、`WorldbookSyncService`）

```sql
ALTER TABLE worldbook_book ADD COLUMN IF NOT EXISTS job_code VARCHAR(32);
```

- 用 `ALTER ... ADD COLUMN IF NOT EXISTS`，因为该文件每次启动执行，改 `CREATE TABLE` 对老库无效（与 `hype_questions` 同一做法）。
- 同步时优先读 YAML 顶层可选字段 `job_code`；没有则取文件名（`java.yml` → `java`）。本期是单值列，一本书只服务一个岗位；要多岗位服务需要另开任务改结构。
- `Worldbook.parse` 增加顶层 `job_code` 的解析（可选字段，不填不报错）。

### 2. DTO 与接口（`dto/worldbook/*`、`WorldbookController`）

- `WorldbookSummary` / `WorldbookDetail` 增加 `jobCode`。
- `GET /api/worldbooks` 支持可选 `jobCode` 过滤；不传行为不变。

### 3. 装载器（新增 `worldbook/WorldbookLoader`）

```java
/**
 * 按岗位把两张表组装成可注入的 Worldbook。
 * 无书 / 无启用条目返回 null，调用方零开销跳过。
 */
Worldbook forJob(String jobCode);
```

- 类放在 `cn.edu.zjut.interview.worldbook` 包内：`Worldbook` 构造器、`Entry` 构造器、`Activation.always()/keyword()` 都是包私有，同包才能直接组装，不必对外暴露内部结构。
- 查 `worldbook_book` 中 `job_code = ? AND enabled = true` 的书（按 `sort_order`）；
- 取该书 `enabled = true` 的条目，按 `sort_order` 还原 `Worldbook.Entry`（`activation_type` + `activation_keys` JSON → `Activation`）；
- `Worldbook` 构造器现在是 private，需要加一个包内可见的静态工厂（如 `Worldbook.of(name, description, entries)`），**不改 `parse` 与 `inject` 行为**。
- 数据量只有 2 本 / 8 条，直接查库即可，暂不做缓存；若后续书变多，再按 `KnowledgeIndexVersion` 的版本号思路加缓存。

### 4. 注入器（新增 `worldbook/WorldbookInjector`）

```java
/** 按会话岗位注入世界书；无书 / 无启用条目时零开销返回。 */
public void inject(InterviewSession session, List<LlmMessage> messages, String userInput);
```

- 内部 `loader.forJob(session.getJobCode())`，拿到书后调 `worldbook.inject(messages, userInput)`。
- 与 `KnowledgeInjector` 的分工：一个管固定岗位背景，一个管按回答检索的片段；两者互不感知，各自只改本轮请求副本。

### 5. 接线一：自由对话（`ChatService`）

在现有 CLOB 注入之后叠加：

```java
worldbookInjector.inject(session, messages, rounds == 0 ? main : null);
```

- `userInput` 只在第 1 轮传（与现有 CLOB 分支、原版 `pre.rs` 一致），keyword 条目不会每轮重复命中。
- 与 CLOB 分支共存：两者都为空则零开销；若将来确认表是唯一真相源，再单独删 CLOB 分支。

### 6. 接线二：剧本链路（`EngineContext` + 两个生成入口）

剧本面试不经过 `ChatService`，只改第 5 步会让答辩主路径静默漏注入，必须单独接：

1. `EngineContext` 增加注入器字段与访问器 `worldbookInjector()`；`InterviewEngine` 有 3 处构造（第 209、352、394 行），另有 5 处测试构造，需一并补参数。
2. `AiDialogueEvent.execute()`：在 `DialogueWriter.writeTurn(...)` 之前调 `ctx.worldbookInjector().inject(ctx.session(), messages, null)`。这里没有玩家原话（`prompt` 是旁白），`userInput` 传 null，只注入 `always`。
3. `InterviewEngine.freeDialogueTurn()`：同样在 `writeTurn` 前调，`userInput` 传本轮 `text`（玩家真实输入），keyword 条目可触发。

不要塞进 `DialogueWriter.writeTurn` 统一处理：它拿不到「本轮该用哪条玩家输入」，`ai_dialogue` 的末条 user 是旁白 prompt，会误触发 keyword。

### 7. 前端

本轮不需要改页面。可选：世界书浏览处显示 `jobCode`（若无对应 UI 则跳过）。

## 六、测试

1. `WorldbookSyncServiceTest`：YAML 有 `job_code` 时以字段为准，没有时回填文件名；重复同步不产生重复行。
2. `WorldbookLoaderTest`：只取 `enabled` 的书与条目；`always` / `keyword` 还原正确；无书返回 null。
3. `ChatServiceTest`（或注入相关测试）：有书时 `always` 进 system、`keyword` 仅第 1 轮按输入命中；注入不写库、不改历史消息。
4. 引擎链路测试：`AiDialogueEvent` 注入 `always` 且 `userInput=null`；`freeDialogueTurn` 用玩家 `text` 触发 `keyword`。
5. 全量 `mvn -o test` 保持 0 失败（当前基线 637）。

## 七、验收标准

- `GET /api/worldbooks` 每本带 `jobCode`（`java` / `frontend`），可用 `?jobCode=java` 过滤。
- 以 `jobCode=java` 开始一场面试：system 中出现 `java.yml` 的 `always` 条目；说一句命中 `keyword` 的话，本轮 user 消息末尾追加对应条目。
- `jobCode=frontend` 的场次只拿到 `frontend.yml`，两本不串。
- 无世界书的岗位（如未配置的岗位）不注入、不报错。
- **两条链路都注入**：分别用剧本入口与自由对话入口各开一场 `jobCode=java` 的面试，两场的 system 里都能看到 `java.yml` 的 `always` 条目；剧本内的自由对话轮还能按关键词触发一次 `keyword` 条目。
- 注入内容不落库：`interview_message` 与请求副本对不上是预期行为，历史消息不被污染。

## 八、非目标

- 不做角色级世界书绑定表（`interviewer_worldbook`）；本方案按岗位即可满足「一本书 = 一个岗位」。
- 不把世界书内容并入 `knowledge` 检索；两者分工见第四节。
- 不做世界书在线编辑 UI。

## 九、风险

- **token 增长**：`always` 条目每轮进 system。必须限制条数与字数，否则与 `knowledge` 注入叠加后会挤压回答空间。
- **内容重复**：若有人把技术知识点也写进世界书，会与 RAG 注入重复；靠语料约定与 review 控制，不做运行时去重。
- **老库兼容**：`job_code` 用 `ALTER` 补列，老库启动即可；但历史 `worldbook_book` 行需要下次启动同步回填（同步是覆盖式，天然满足）。

## 十、顺带发现（不纳入本次范围）

- **知识注入（`KnowledgeInjector`）在剧本链路同样缺失**：`engine` 包内 0 命中，剧本面试不会做 K4 的 top-3 知识注入。与本次世界书注入是同一类「只接了自由对话」问题，属于 K4 的历史缺口，建议单开任务评估，本 issue 不处理。
