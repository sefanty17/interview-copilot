# 类加载与双亲委派模型
## 类加载完整生命周期
面试官常问：Java类从编译成class文件到内存中可用，会经历哪几个阶段？每个阶段做什么？
答题要点：类加载分为加载、验证、准备、解析、初始化5个核心阶段，使用后还有卸载。加载阶段是通过类全限定名读取class字节流到JVM，生成Class对象；验证校验字节码格式、语义、字节码指令合法性，防止恶意代码；准备阶段为静态变量分配内存、赋默认初始值，不是业务赋值；解析把符号引用转为直接引用；初始化执行静态代码块、静态变量赋值，是真正执行用户代码的阶段。只有主动引用才会触发初始化，被动引用不会触发。
常见误区：很多人以为准备阶段会给静态变量赋业务值；实际上准备阶段只有默认值，static final编译期常量会在准备阶段直接赋值，普通static变量要等到初始化阶段。另外，类卸载不是GC一定会做，需要满足类加载器、类对象、实例全部不可达，条件很苛刻。

## 双亲委派机制流程
面试官常问：什么是双亲委派？双亲委派的执行流程是什么？
答题要点：双亲委派是类加载器的委托规则：收到类加载请求，先交给父加载器，父加载器逐层向上委托，直到顶层启动类加载器；父加载器无法加载时，才由当前加载器自己加载。加载器层级：启动类加载器Bootstrap（C++实现，加载jdk核心rt.jar）、扩展类加载器Extension、应用程序类加载器AppClassLoader，还有自定义类加载器。
常见误区：双亲委派不是“父加载器优先加载所有类”，是**先委托父加载尝试加载**，父加载失败才自己加载；不是继承关系，是组合持有的parent引用，不是类继承。

## 双亲委派的作用与破坏场景
面试官常问：为什么要设计双亲委派？哪些场景需要破坏双亲委派？
答题要点：核心两个目的：沙箱安全，防止自定义java.lang.String这类核心类，覆盖JDK原生类；保证类的全局唯一性，同一个类全限定名，在同一个加载器下只加载一次。破坏场景：SPI机制（JDBC，驱动由App加载，但是需要Bootstrap加载的接口，线程上下文类加载器打破委派）、热部署、自定义加密类加载。
常见误区：很多人认为双亲委派是强制语法，实际上它是AppClassLoader实现的约定，自定义类加载器重写loadClass就可以跳过；JDBC破坏双亲委派不是修改loadClass，是使用Thread.getContextClassLoader。

## 自定义类加载器实现思路
面试官常问：手写一个自定义类加载器，需要重写哪个方法？为什么？
答题要点：推荐重写findClass，而不是loadClass。loadClass是实现双亲委派逻辑的入口，重写它会直接破坏委派规则；findClass是父类预留的模板方法，负责读取字节流、defineClass生成Class对象。典型场景：加密class文件，自定义加载器解密后再加载。
常见误区：新手直接重写loadClass，写完之后双亲委派直接失效，引发重复加载、安全风险；defineClass只能调用一次，同一个字节流不能反复define。
