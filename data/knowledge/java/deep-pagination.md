# MySQL 深分页优化
## limit offset 深分页问题
面试官常问：limit 100000,10 为什么慢？
答题要点：limit offset,size 数据库会扫描offset+size行，丢弃前面offset行，返回后面size行。offset越大，扫描行数越多，IO开销巨大，索引即使命中，也要回表大量数据。
常见误区：加了索引深分页就很快；索引只能减少排序开销，无法跳过前面offset行，依旧要扫描。

## 主键书签分页（延迟关联）
面试官常问：书签分页（id>上一页最大id）原理，适用场景？
答题要点：前提：有序、连续自增主键，无删除。where id > last_id limit size，利用主键索引直接定位起点，不需要扫描前面数据。如果有删除id空洞，页面会少数据。
常见误区：书签分页万能；只适合按主键排序；业务需要按创建时间、非主键字段排序，不能直接用。

## 延迟关联、子查询优化
面试官常问：非主键排序的深分页，延迟关联写法？
答题要点：先在覆盖索引里查出需要的主键id，再用in或者join回表查完整数据。`select t.* from table t join (select id from table where ... order by xx limit 100000,10) tmp on t.id=tmp.id`；子查询只走索引，不回表，减少回表开销。
常见误区：子查询一定更快；子查询必须命中覆盖索引，否则优化失效。

## 业务方案兜底
面试官常问：深分页还有哪些业务层方案？
答题要点：禁止无限翻页，前端只提供上一页、下一页，不提供跳页；大结果集导出走游标、异步导出；ES搜索引擎分页，ES也有深分页坑，同样用search_after书签。
常见误区：数据库必须支持随便跳转到第1000页；业务上不推荐，成本极高，优先产品方案限制。
