# 消息队列顺序、幂等、积压
## 消息顺序性
面试官常问：MQ怎么保证消息有序？全局有序和局部有序？
答题要点：全局有序：整个topic所有消息严格顺序，只能一个分区，吞吐量极低；业务几乎不用。局部有序：同一业务标识（订单id）哈希到同一个分区，分区内消息有序，是主流方案。
常见误区：MQ天然全局有序；分区内有序，分区之间无序；RocketMQ、Kafka都是分区有序。

## 消息幂等
面试官常问：为什么消息会重复？怎么实现消费幂等？
答题要点：重复原因：网络抖动、ACK丢失、消费者宕机，Broker重试投递。幂等方案：唯一业务key，消费前查本地幂等表；数据库唯一索引；Redis去重。
常见误区：MQ可以保证只投递一次；所有MQ都只能保证至少一次（at-least-once），业务必须做幂等。

## 消息积压
面试官常问：消息大量积压怎么排查、怎么处理？
答题要点：先定位：消费速度远小于生产速度；消费逻辑慢、数据库慢、线程太少。应急方案：扩容消费者、临时分流、清理无效消息；根治：优化消费逻辑、批量消费、异步化非核心逻辑。
常见误区：积压直接加分区就一定提速；Kafka分区数是消费者上限，消费者不能超过分区数；RocketMQ可以多线程消费同一个分区。

## 消息丢失场景
面试官常问：消息丢失在哪些环节？怎么避免？
答题要点：生产者丢失：没等ACK；Broker丢失：刷盘策略；消费者丢失：处理完业务前提交offset。保障：生产者确认、Broker同步刷盘、业务处理成功再提交位点。
常见误区：同步刷盘不会丢消息；同步刷盘性能差，线上一般用异步刷盘配合副本机制。
